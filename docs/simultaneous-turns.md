# 同时回合制

经典模式通过 `data/rules/classic.json` 的 `simultaneous` 节点声明同时回合制能力。创建房间时，前端将 `config.turnMode` 设置为 `simultaneous`；未勾选时使用 `sequential`。

## 回合阶段

服务器在同时回合制中维护 `planning`、`resolving` 和 `ended` 阶段。双方都提交规划后，服务器依次执行部署、射击和移动。对手的具体规划不会通过 `publicState` 泄露，只会发送双方是否已提交。

## 规划格式

每个玩家的规划包含 `deployments` 和按单位编号索引的 `actions`。一个行动可以同时包含 `shootTargetId` 与 `moveTo`。部署只记录意图，结算时才创建单位；本回合新部署单位不能行动。

规划对象可以通过服务器的 `serializePlan` 和 `deserializePlan` 转换为 JSON 文本，便于日志、回放或后续持久化。网络层使用同一 JSON 数据结构，不把规划写死在前端状态中。

## 结算顺序

1. 双方部署在同一格时，服务器随机选择一方；失败方不部署。
2. 所有合法射击基于规划结束时的位置同时计算。已提交射击的单位即使在本轮射击中死亡，射击仍然生效。
3. 射击造成的伤害累计，达到规则文件中的击杀阈值后统一移除死亡单位。
4. 移动使用射击后的棋盘。路径中的中间格和最终格逐步争夺；冲突点独立随机选择胜者。中间格或最终格失败都会使该单位回到原点，不自动改道。
5. 移动结束后判定胜负；若未结束则进入下一回合规划阶段。

移动请求只提交目标格，不提交路径。服务器按照地图连接表进行确定性的最短路径搜索；如果存在多条等长路径，使用连接表中的先后顺序。为避免交换和穿越歧义，路径不能经过本轮结算开始时仍被其他存活单位占据的格子。

## 超时与扩展

`planningTimeoutMs` 控制规划超时。超时会为未提交的一方提交空规划。玩法可以在自己的规则 JSON 中关闭同时回合制、禁止同时射击和移动，或更换冲突策略；服务器对未知玩法能力会安全降级为轮流回合制或拒绝不支持的配置。
